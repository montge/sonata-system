# Kria KR260 target

The `synth_kr260` target builds the Sonata system for the AMD Kria K26 system-on-module (Zynq UltraScale+ MPSoC, part `xck26-sfvc784-2LV-c`) mounted on the KR260 Robotics Starter Kit carrier.
It is the same `sonata_system` as the Sonata One and Sonata XL bitstreams with a different board layer: a new top level `rtl/fpga/top_kr260.sv`, its own constraint files, and a Tcl script that creates the processing-system (PS) IP the top level needs.
The aim is to keep the difference from `synth_xl` as small as possible so the target is cheap to rebase on upstream.

The general build instructions in [FPGA development](fpga-development.md) apply; this page covers only what the KR260 does differently.

## Status

**Nothing has been synthesised or run on hardware yet.**
The files exist and the `lint_kr260` target elaborates the top level with Verilator against a stand-in for the PS IP (at the time of writing it still stops on lint warnings in the upstream `rtl/fpga/rst_ctrl.sv` and `rtl/fpga/padring.sv`, which the upstream `lint` target never sees because `top_verilator` does not use them), but:

- the pin constraints in [`data/pins_kr260.xdc`](../../data/pins_kr260.xdc) are a draft: the PMOD1 package pins are marked `VERIFY` (taken from third-party board files, not from the KR260 user guide UG1092 or the schematic) and every other pin is a commented-out `TODO`;
- the timing constraints in [`data/synth_timing_kr260.xdc`](../../data/synth_timing_kr260.xdc) have not been read by Vivado, and the clock names they rely on (`clk_pl_0`, `clk_pl_1`) are what the PS IP is expected to create, not what has been observed;
- [`flow/kr260_ps.tcl`](../../flow/kr260_ps.tcl) uses `CONFIG.*` property names of the `zynq_ultra_ps_e` IP that have not been checked against a Vivado release;
- the PS8 primitive's pin name used as the source of the generated SPI clocks has not been checked;
- utilisation, timing closure and the Kria loading flow are all unverified.

Treat every number and name on this page that depends on the above as unconfirmed until a Vivado run and a board session have been recorded.

## How it differs from Sonata One and Sonata XL

| Area | Sonata One / XL | KR260 |
|------|-----------------|-------|
| Device | Artix-7 (`xc7a50t` / `xc7a200t`) | Zynq UltraScale+ K26 SOM (`xck26-sfvc784-2LV-c`) |
| Top level | `rtl/fpga/top_sonata.sv` | `rtl/fpga/top_kr260.sv` |
| Clocks | 25 MHz oscillator into `clkgen_sonata` (`PLLE2_ADV`), which makes `clk_sys` (40 MHz), `clk_usb` (48 MHz) and the HyperRAM clocks | No PLL or MMCM in the programmable logic. The Zynq PS drives `pl_clk0` (40 MHz) as `clk_sys` and `pl_clk1` (48 MHz) as `clk_usb`; the HyperRAM clocks are tied off as on Sonata XL |
| Reset | Reset button into `rst_ctrl`, gated by PLL lock | The PS's active-low `pl_resetn0` into `rst_ctrl`, with `pll_locked_i` tied high (the PS clocks are stable before the PL is configured) |
| HyperRAM | 1 MiB HyperRAM chip (One); 1 MiB faux-HyperRAM in block RAM (XL) | 256 KiB faux-HyperRAM in block RAM (`USE_HYPERRAM_SRAM_MODEL` with `HyperRAMSize=262144`); 1 MiB does not fit the K26's 5.1 Mb of block RAM next to the 128 KiB SRAM |
| ADC | `XADC` hard block behind the [ADC](../ip/adc.md) registers | UltraScale+ has no `XADC` and the carrier routes no analogue pins to the PL, so under `TARGET_KR260` `rtl/ip/xadc/rtl/xadc.sv` instantiates a stub that completes every access, returns zero data and ignores writes. The memory map is unchanged |
| Device DNA | `DNA_PORT` (57 bits) in [System info](../ip/system_info.md) | `DNA_PORTE2` (96 bits, same five ports) under `TARGET_KR260`; the bit-serial register interface is unchanged. `dv/models/fpga/rtl/DNA_PORTE2.v` is the simulation model |
| USB device | USB transceiver on the board | No transceiver on the PL. The [USB device](../ip/usb.md) block stays instantiated and clocked so the bus map and interrupt numbering do not change; its receive inputs and VBUS sense are tied inactive and its outputs go nowhere |
| Board I/O | LCD, Ethernet MAC, microSD, SPI flash, RS-232/485, QWIIC, Arduino shield, mikroBUS, switches, LEDs, three PMODs, Raspberry Pi header | Four PMODs and the Raspberry Pi header (all 3.3 V). Everything else is tied off; see [What is tied off](#what-is-tied-off) |
| Console and debug | UART0 and the debug-module JTAG go to the on-board FTDI | UART0 and the debug-module JTAG go to PMOD1 (J2) for an external 3.3 V USB-serial adapter and an external JTAG probe. The KR260's own USB-JTAG is attached to the MPSoC chain, not to PL pins |
| Firmware | Boot loader in SRAM loads the application from SPI flash | No flash. Bake the application into the SRAM with `SRAMInitFile`, or load it over JTAG |
| Loading the bitstream | USB drive, openFPGALoader or Vivado | Linux on the PS loads the PL as a Kria firmware app (`xmutil loadapp`); the device-tree overlay sets the PL clock rates |

The pinmux indices of `sonata_pkg` (`IN_PIN_*`, `OUT_PIN_*`, `INOUT_PIN_*`) are the same as on Sonata, so the sonata-software board description and its [pinmux](../ip/pinmux/README.md) driver work unchanged; signals with no KR260 pin simply read their idle level.

## Parameters

Set on the `fusesoc` command line as `--Name=value`.

| Parameter | Kind | `synth_kr260` value | Meaning |
|-----------|------|---------------------|---------|
| `SRAMInitFile` | `vlogparam` | upstream default (`sw/cheri/build/boot/boot_loader.vmem`) | Initial contents of the 128 KiB SRAM. The default is Sonata's boot loader, which waits for a SPI flash the KR260 does not have, so always pass the `.vmem` of the application you want to run (see [Building](#building)) |
| `HyperRAMSize` | `vlogparam` | `262144` | Size in bytes of the on-chip RAM at the HyperRAM address `0x4000_0000`. Flows from `sonata.core` through `top_kr260` to `sonata_system`. The default elsewhere (`sim`, `synth_xl`) is 1 MiB |
| `TARGET_KR260` | `vlogdefine` | `true` | Selects the XADC stub and `DNA_PORTE2`. Can also be given to the `sim` target to simulate the KR260 flavour |
| `USE_HYPERRAM_SRAM_MODEL` | `vlogdefine` | `true` | SRAM model instead of the HyperRAM controller, as on Sonata XL |
| `PRIM_DEFAULT_IMPL` | `vlogdefine` | `prim_pkg::ImplXilinx` | Xilinx primitives (`IOBUF` in the padring and so on); these exist on UltraScale+ |

`top_kr260` also has the module parameters `SysClkFreq` (40,000,000) and `HyperRAMClkFreq` (100,000,000, passed through and unused).
`SysClkFreq` is what the UART and timer code assumes; it must equal the `pl_clk0` rate set in `flow/kr260_ps.tcl` and in the device-tree overlay.

## Building

With Vivado on the `PATH` and the Python environment from [FPGA development](fpga-development.md), from the repository root:

```sh
fusesoc --cores-root=. run --target=synth_kr260 --setup --build lowrisc:sonata:system \
  --SRAMInitFile=$PWD/sw/cheri/build/tests/uart_check.vmem
```

The `.vmem` comes from [building the baremetal software](../guide/building-examples.md#baremetal-examples); `util/mem_helper.sh rtos_img -e app.elf -v app.vmem` converts any ELF into the layout the SRAM expects.
The bitstream is written to `build/lowrisc_sonata_system_0/synth_kr260-vivado/lowrisc_sonata_system_0.bit`.

What the target does beyond `synth_xl`:

- `flow/kr260_ps.tcl` runs after the sources are added and creates the `zynq_ultra_ps_e` IP instance `zynq_ultra_ps_e_0` with `pl_clk0` at 40 MHz, `pl_clk1` at 48 MHz and no AXI ports. `top_kr260` instantiates it as `u_ps`.
- The PS derives `pl_clk0` from one of its PLLs through two 6-bit integer dividers, so the exact rate depends on the PLL frequency the boot firmware configured (a 1.5 GHz IOPLL gives 40.54 MHz or 39.47 MHz, a 1.2 GHz PLL gives 40 MHz exactly). The UART tolerates the 1.4 % error; the timer runs correspondingly fast or slow. Read the real rate from `/sys/kernel/debug/clk/clk_summary` on the board and record it here; if an exact rate matters, 37.5 MHz and 50 MHz are exact from a 1.5 GHz PLL and need only `SysClkFreq`, `flow/kr260_ps.tcl` and the overlay changed together.
- `data/pins_kr260.xdc` and `data/synth_timing_kr260.xdc` replace the Sonata constraint files; `data/impl_timing.xdc` and `flow/vivado_setup.tcl` are shared.

The top level can be linted without Vivado; `dv/models/fpga/rtl/zynq_ultra_ps_e_0.sv` stands in for the PS IP and must never be in a synthesis fileset:

```sh
fusesoc --cores-root=. run --target=lint_kr260 --tool=verilator --setup --build lowrisc:sonata:system
```

## Packaging and loading on the board

The PS on a Kria board boots Linux from the SD card and loads the PL afterwards through the FPGA manager, so there is no JTAG programming of the PL.
The standard mechanism is a *firmware app*: a directory under `/lib/firmware/xilinx/` holding the bitstream as a `.bit.bin`, a device-tree overlay `.dtbo` and a `shell.json`, which `xmutil loadapp` loads.
`bootgen` ships with Vivado and Vitis.

```sh
# on the build host
cat > sonata.bif <<BIF
all: { [destination_device = pl] build/lowrisc_sonata_system_0/synth_kr260-vivado/lowrisc_sonata_system_0.bit }
BIF
bootgen -arch zynqmp -image sonata.bif -process_bitstream bin -w -o sonata_kr260.bit.bin
dtc -@ -O dtb -o sonata_kr260.dtbo sonata_kr260.dtso

# on the board
sudo mkdir -p /lib/firmware/xilinx/sonata_kr260
sudo cp sonata_kr260.bit.bin sonata_kr260.dtbo shell.json /lib/firmware/xilinx/sonata_kr260/
sudo xmutil unloadapp
sudo xmutil loadapp sonata_kr260
```

`sudo fpgautil -b sonata_kr260.bit.bin -o sonata_kr260.dtbo` is the lower-level alternative to `xmutil`.
Unloading and loading the app again restarts the baked-in firmware from its initial state.

`shell.json` is the two-line descriptor `xmutil` requires:

```json
{
  "shell_type": "XRT_FLAT",
  "num_slots": "1"
}
```

The overlay names the bitstream, lists the PL reset so the FPGA-region driver asserts it around programming, and sets the two PL clocks.
It is where the clock rates are actually enforced at run time: the `FREQMHZ` settings in `flow/kr260_ps.tcl` only drive timing analysis, and without the overlay the kernel leaves `pl_clk0` at its default (often 100 MHz), which the design is not timed for.
The essential nodes are:

```dts
&fpga_full {
	firmware-name = "sonata_kr260.bit.bin";
	resets = <&zynqmp_reset 116>;   /* ZYNQMP_RESET_PS_PL0 */
};

&amba {
	clocking0: clocking0 {
		compatible = "xlnx,fclk";
		#clock-cells = <0>;
		clocks = <&zynqmp_clk 71>;  /* PL0_REF */
		assigned-clocks = <&zynqmp_clk 71>;
		assigned-clock-rates = <40000000>;
		clock-output-names = "fabric_clk0";
	};
	clocking1: clocking1 {
		compatible = "xlnx,fclk";
		#clock-cells = <0>;
		clocks = <&zynqmp_clk 72>;  /* PL1_REF */
		assigned-clocks = <&zynqmp_clk 72>;
		assigned-clock-rates = <48000000>;
		clock-output-names = "fabric_clk1";
	};
};
```

The maintained copies of `sonata_kr260.dtso` and `shell.json`, together with the build reports, live in the `boards/kr260/` directory of the cheri-dev repository that carries this port, not in this repository.
The clock IDs 71 and 72 and reset 116 were checked against the `linux-xlnx` device-tree bindings; confirm them against the kernel running on your board if the UART baud rate comes out wrong.

### Console and JTAG

- Console: a 3.3 V USB-serial adapter on PMOD1 (J2) pins 1 (TX from the FPGA) and 2 (RX into the FPGA), ground on pin 5 or 11; 921600 baud, 8N1, the Sonata default.
- Debug: an external FTDI-based JTAG probe on PMOD1 (J2) pins 3, 4, 7 and 8, driven by OpenOCD with [`util/kr260-openocd-cfg.tcl`](../../util/kr260-openocd-cfg.tcl) (the probe is chosen with the `KR260_JTAG_ADAPTER` environment variable, see the file):

```sh
util/mem_helper.sh load_program -e app.elf -t util/kr260-openocd-cfg.tcl
```

Loading over JTAG avoids a re-synthesis per firmware image.

## Connections

PMOD pin numbers are the Digilent 12-pin numbering: data on pins 1-4 and 7-10, ground on 5 and 11, 3.3 V on 6 and 12.
The Sonata `pmod0[0..7]` / `pmod1[0..7]` bits are Pmod data pins 1, 2, 3, 4, 7, 8, 9, 10 in that order, as on Sonata.
The KR260 has 60 PL header data pins (4 x 8 PMOD + 28 Raspberry Pi) and Sonata would need 64, so Sonata's `pmodc[5:0]` is not brought out: `top_kr260` ties its six pinmux indices off like the Arduino header pins.

| Sonata signal | KR260 connector | Note |
|---------------|-----------------|------|
| `ser0_tx`, `ser0_rx` | PMOD1 (J2) pins 1, 2 | Console UART0, dedicated pins |
| `tck_i`, `tms_i` | PMOD1 (J2) pins 3, 4 | Debug-module JTAG TCK, TMS |
| `td_i`, `td_o` | PMOD1 (J2) pins 7, 8 | Debug-module JTAG TDI, TDO |
| `usrLed[7:0]` | PMOD4 (J20) pins 1, 2, 3, 4, 7, 8, 9, 10 | GPIO outputs 0-7, for external LEDs (`usrLed[0]` on pin 1) |
| `pmod0[7:0]` | PMOD2 (J18) | Pinmuxed, Sonata PMOD0 semantics |
| `pmod1[7:0]` | PMOD3 (J19) | Pinmuxed, Sonata PMOD1 semantics |
| `pmodc[5:0]` | not brought out | Its pinmux indices read 0; outputs dropped (no spare header pins) |
| `rph_g0` .. `rph_g27`, `rph_txd0`, `rph_rxd0` | Raspberry Pi header | Each on the same-named Raspberry Pi GPIO; I2C1 on GPIO2/3, SPI0 on GPIO7-11, SPI1 on GPIO16-21, UART on GPIO14/15, HAT ID on GPIO0/1 |

Package pins: see [`data/pins_kr260.xdc`](../../data/pins_kr260.xdc) for what is `VERIFY` and what is `TODO`.
The carrier has no PL-connected user LED that has been confirmed, so LEDs are external.

## What is tied off

`top_kr260` gives every Sonata signal that has no KR260 counterpart a defined idle value, so software reading the related registers gets a defined result:

| Sonata feature | KR260 handling |
|----------------|----------------|
| User switches, joystick, selector switches | GPIO inputs read 0 (off) |
| microSD card detect | Reads 1 (card absent); microSD DAT0 reads 0, CMD/CLK/DAT3 outputs dropped |
| GPIO outputs above `usrLed[7:0]` | Dropped |
| CHERI error indicators (9), CHERI enable LED, RGB LED, status LEDs | Not connected to any pin |
| LCD SPI | Outputs dropped, CIPO reads 0 |
| Ethernet MAC SPI and interrupt | Outputs dropped, CIPO reads 0, interrupt never asserted |
| USB transceiver | `usb_dp_i`, `usb_dn_i`, `usb_rx_d_i` read 0, VBUS sense reads 0 (absent); outputs dropped; the block is still clocked by `clk_usb` so its registers and interrupt line behave as on Sonata |
| UART1, RS-232, RS-485 | RX lines read idle high, TX and the RS-485 enables dropped |
| mikroBUS | SPI CIPO reads 0, UART RX reads 1, I2C lines read 1 (idle), outputs dropped |
| QWIIC I2C buses (0 and 1) | SCL/SDA read 1 (idle, pulled up) |
| Arduino shield digital pins | Read 0; analogue inputs read 0 and the ADC block returns 0 |
| SPI flash | D1 (CIPO) reads 0, outputs dropped |
| HyperRAM pins | Stay on internal wires; the SRAM model does not drive them |
| HyperRAM clocks and reset | Tied to 0, as `sonata_system` does for Sonata XL |

## Memory map

Every base address is the same as on Sonata; only the large RAM region differs in size.

| Region | Base | Sonata One | KR260 |
|--------|------|------------|-------|
| SRAM | `0x0010_0000` | 128 KiB, tagged | Unchanged |
| Revocation tags | `0x3000_0000` | sized from the SRAM | Unchanged |
| HyperRAM region | `0x4000_0000` | 1 MiB HyperRAM, tagged | 256 KiB of on-chip RAM, tagged (`HyperRAMSize`). The crossbar window is still 1 MiB (`ADDR_MASK_HYPERRAM` in `rtl/bus/tl_main_pkg.sv` is `0xfffff`), and the SRAM model only decodes the low address bits, so addresses from `0x4004_0000` to `0x400f_ffff` alias onto the 256 KiB below them. Software must stay within the documented size |
| Peripherals | `0x8000_0000` .. | per `tl_main_pkg.sv` | Unchanged, including the [ADC](../ip/adc.md) at `0x8000_b000`, whose registers read as 0 |
| Debug module | `0xb000_0000` | | Unchanged |

A sonata-software image that stays within 256 KiB of the HyperRAM region therefore runs without a new linker layout.
Raising the region to 1 MiB needs the SRAM model's storage to go into UltraRAM (the K26 has 18 Mb of it); that is a follow-up, not part of this target.
